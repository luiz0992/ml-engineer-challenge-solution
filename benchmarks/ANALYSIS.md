# Optimisation Analysis

Interpretation of the measurements in [`README.md`](README.md), which is
regenerated by `models/optimisation/run_benchmarks.py` and contains only raw
data. This document holds the conclusions and the reasoning behind the
deployment recommendation.

Hardware: NVIDIA RTX 5000 Ada (32 GiB, sm_89), CUDA 12.8, ONNX Runtime 1.29,
TensorRT 10.16. Model: ViT-Small/16 at 224x224, 200 classes, 21.7M parameters.

---

## 1. Headline results

| Configuration | Batch 32 latency | Throughput | Speedup | Top-1 |
| --- | ---: | ---: | ---: | ---: |
| PyTorch eager FP32 (baseline) | 16.78 ms | 1,907 img/s | 1.00x | 87.25% |
| PyTorch eager bf16 | 5.23 ms | 6,118 img/s | **3.21x** | 87.25% |
| ONNX Runtime TensorRT FP16 | 3.49 ms | 9,177 img/s | **4.81x** | 87.25% |
| ONNX Runtime CUDA FP32 | 18.86 ms | 1,696 img/s | 0.90x | 87.25% |
| ONNX Runtime CPU INT8 | 475 ms | 67 img/s | 0.04x | 81.85% |

Single-image latency is **1.05 ms** under TensorRT, comfortably inside the
challenge's sub-second requirement with three orders of magnitude to spare.

---

## 2. INT8 quantization cost more accuracy than expected

Static post-training quantization cost **5.4 points of top-1 accuracy**
(87.25% -> 81.85%). That is a poor trade and the reason INT8 is *not*
recommended for deployment here.

Reaching even that figure required work. The default min-max calibration was
catastrophic, and the fix is worth recording:

| Calibration method | Top-1 | Drop vs FP32 |
| --- | ---: | ---: |
| MinMax (ONNX Runtime default) | 70.70% | -17.70pp |
| Entropy | 70.70% | -17.70pp |
| Percentile 99.999 | 80.50% | -7.90pp |
| **Percentile 99.99** | **82.90%** | **-5.50pp** |
| Percentile 99.99, classifier head excluded | 82.80% | -5.60pp |

*(Measured on 1,000 validation images; the 81.85% headline figure uses 2,000.)*

**Why min-max fails on vision transformers.** Min-max sets the quantization
range from the single most extreme activation seen during calibration.
LayerNorm and GELU in ViTs produce rare outliers orders of magnitude above the
typical activation. One outlier stretches the range so far that ordinary values
collapse into a handful of the 256 available levels. Percentile calibration
discards the top 0.01% of observations, keeping resolution where the data
actually lives, and recovers 12 points of accuracy.

**Two negative results worth stating.** Entropy calibration performed
*identically* to min-max, so it is not an alternative fix. Excluding the
classifier head from quantization changed nothing (-5.60pp vs -5.50pp), which
means the residual loss is spread across the network rather than concentrated
in one sensitive layer. Closing the remaining gap would require
quantization-aware training or a ViT-specific scheme such as SmoothQuant — not
further layer exclusions. That was worth establishing before spending more time
on PTQ tuning.

**INT8 was also slow.** On CPU it reached only 1.3x the FP32 CPU throughput,
far below the ~4x the 3.8x model-size reduction might suggest. Symbolic shape
inference fails on this graph (see section 5), so fewer nodes were quantized
than ideal, and the QDQ nodes that remain add dequantise/requantise overhead
that partly cancels the integer speedup.

---

## 3. bf16 is the best effort-to-reward ratio

bf16 required a single configuration flag and delivered **3.21x** with **zero**
accuracy change — the exponent range matches fp32, so no loss scaling is needed
and no values overflow. For most teams this is the correct place to stop.

TensorRT delivers a further 1.5x over bf16, but costs an engine build per input
shape (minutes), a cache to manage, a hardware-specific artefact that is not
portable across GPU architectures, and a fragile library-loading story
(section 5). Worth it at scale; poor value for a low-traffic service.

---

## 4. ONNX Runtime CUDA is slower than PyTorch

ONNX Runtime on the CUDA provider was consistently **slower than eager
PyTorch** (0.90x at batch 32) — the opposite of the usual expectation that
exporting a graph makes it faster.

The reason is that the comparison is not like-for-like. PyTorch dispatches ViT
attention to a fused SDPA kernel (FlashAttention), while the exported ONNX graph
decomposes attention into discrete MatMul, Div, Softmax, and Transpose nodes
that the CUDA provider executes separately, paying memory-bandwidth cost at each
step. TensorRT wins precisely because it re-fuses those nodes during engine
building.

The practical conclusion: **ONNX export is valuable for portability and as the
route to TensorRT, not as a speedup in itself.** A team exporting to ONNX and
expecting a free win on the CUDA provider would be disappointed.

---

## 5. Two failures that would have been silent

Both are worth calling out because each would have produced a *plausible but
wrong* benchmark table.

**TensorRT falling back to CPU.** ONNX Runtime advertises
`TensorrtExecutionProvider` in `get_available_providers()` even when the
underlying libraries cannot be loaded. Session creation then logs a warning and
silently falls back to CPU. Benchmarking would have reported CPU numbers under
a "tensorrt" label — roughly 100x too slow, and easy to rationalise as "TensorRT
must need tuning".

Two guards address this. `benchmark_onnx` asserts that the provider ONNX
Runtime actually selected matches the one requested, and raises otherwise.
`ensure_tensorrt_loadable` preloads `libnvinfer`, `libnvonnxparser`, and
`libcudnn` with `RTLD_GLOBAL`, since the pip wheels install them to
directories the dynamic linker does not search. Setting `LD_LIBRARY_PATH` from
inside the process would be too late — the linker reads it at exec time.

The root cause was a CUDA major-version mismatch: `tensorrt-cu13` against an
otherwise CUDA 12 stack. `pyproject.toml` now pins `tensorrt-cu12` explicitly.

**A mis-anchored speedup baseline.** The report initially keyed its baseline on
backend name alone. Because `pytorch` labelled CPU, CUDA, fp32, and bf16 runs
identically, the dictionary comprehension kept whichever ran last — the bf16
row — and every speedup in the table was quietly computed against it. bf16
showed exactly `1.00x`, which is what exposed it. Backend labels now include
the device, and the baseline is matched on backend *and* precision.

---

## 6. Recommendation

**Serve bf16 on GPU.** It is 3.21x faster than fp32 baseline, loses no
accuracy, needs one config flag, and has no build-time or portability cost.

**Add TensorRT FP16 if throughput demands it.** A further 1.5x (4.81x total,
9,177 img/s), at the cost of per-shape engine builds and non-portable
artefacts. The API's model service supports it as a selectable backend with
fallback, so it can be enabled per deployment.

**Do not deploy INT8 for this model.** It costs 5.4 points of accuracy for a
1.3x CPU speedup, and is slower than every GPU configuration. INT8 would only
make sense for a CPU-only deployment where the accuracy loss is acceptable, and
even then quantization-aware training should be tried first.

The exported FP32 ONNX file remains the portable interchange artefact and the
input to TensorRT engine building, so it is retained regardless.

---

## Reproducing

```bash
uv run python -m models.optimisation.run_benchmarks \
    --batch-sizes 1 8 32 --iterations 100 --accuracy-samples 2000
```

First run builds TensorRT engines (several minutes) and caches them under
`models/artifacts/onnx/trt_cache/`. Subsequent runs reuse the cache. Add
`--skip-tensorrt` on machines without it; the sweep degrades gracefully and
reports the remaining backends.
